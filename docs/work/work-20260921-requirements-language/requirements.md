# 需求：需求探索詢問與交付文件語言

## 目標

修正 Megin Skills-only 流程，讓需求探索在重大資訊不足時真正與使用者對談並停在需求階段，同時讓所有新產出的交付文件以繁體中文呈現，保留 AI 技能指令及技術控制內容的英文可執行性。

## 使用者與範圍

使用者是透過 Codex 使用 Megin Skills 的開發者。範圍包含需求入口、需求探索、技術規劃及其餘會產出人類可讀工作文件的階段規則；不包含 Quartz.NET Template 實作、既有文件全文翻譯或遠端交付。

## 已知問題

現行規則只要求「一次問一個問題」，沒有規定重大未知時必須等待回答，也沒有定義人類可讀文件的語言。現行 `workflow-record.md` 範本與 Skills 指令為英文，因此另一個專案會得到英文的 `requirements.md` 與 `workflow.md`。

## 需求

- 在需求入口、需求探索及技術規劃中共用「重大未知必須提問並停等」規則。
- 可由專案查明的事實先查證；用途、受眾、邊界、驗收與產品取捨不可自行假設已確認。
- 尚未釐清時以 `phase: requirements`、`status: awaiting_user` 記錄，不能宣稱需求完成或交接至規劃。
- 資訊已完整時不為形式而追加問題。
- 新的需求、流程、計畫、診斷、審查、驗證、驗收與知識文件的可讀文字使用繁體中文。
- 技能指令、欄位鍵、狀態值、識別碼、路徑、指令、程式碼、原始工具輸出及 Gherkin 關鍵字維持英文；Gherkin 情境敘述使用繁體中文。
- 語言規則集中於共用政策檔，所有會產出交付文件的 Skills 直接引用該政策。
- `workflow-record.md` 的範本可讀文字改為繁體中文，保留既有 schema 與控制值。
- 重建 `megin-skills.zip`，確保安裝包與來源位元組一致。

## 不在範圍

- 不建立或實作 Quartz.NET Template。
- 不翻譯既有 README、OPERATIONS、歷史工作紀錄或既有封存內容。
- 不新增獨立的需求核准關卡；既有計畫核准仍是唯一計畫閘門。

## 風險與假設

若使用者只提供「完整實現所有功能」等廣泛描述，流程只能確認需求探索尚未完成，不能把功能清單當成已核准範圍。語言政策以繁體中文作為人類可讀內容的預設；專案或使用者明確指定其他語言時，該明確指定優先。

## 驗收標準

1. `REQ-LANG-001`：Quartz.NET 廣泛需求會先收到繁體中文的最高影響澄清問題，且不產生完整功能承諾或進入規劃。
2. `REQ-LANG-002`：使用者回答仍不足時，下一輪繼續提出一個重大未知問題並維持需求階段。
3. `REQ-LANG-003`：需求已包含用途、受眾、範圍與驗收時，直接建立需求文件，不追加形式問題。
4. `REQ-LANG-004`：新建工作紀錄及所有階段產出的可讀文字為繁體中文，技術控制值仍可被既有工具解析。
5. 來源 Skills 與 `megin-skills.zip` 通過既有封裝驗證且內容完全一致。
