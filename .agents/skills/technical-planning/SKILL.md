# 技術規劃

把來源規格的 `WHAT` 與專案證據、技術限制結合成可審閱的 `HOW`。`證據門檻` 是進入 Candidate 前的關卡；`阻塞未知` 是任何未解決就會改變規格、設計、測試策略或工作包的事項。

## 邊界

- 規劃活動限於唯讀查證、對話中的 Candidate 草稿，以及核准後的規劃 artifacts；產品程式碼、外部 tickets、部署狀態與無關架構維持原狀。
- 來源規格決定行為；適用的治理、ADR 與既有契約限制技術方案。衝突進入證據門檻，由決策者裁定。
- 明確技術限制優先；其餘選擇沿用有證據的專案慣例。
- 使用使用者的主要語言成文，保留必要的技術原文與來源識別碼。
- 秘密只以提供機制或位置描述；不得在輸出、對話或提示中重現秘密值。
- Candidate 與全部精確路徑獲明確核准前，工作區與外部狀態保持唯讀；核准後只寫入[交付協定](references/delivery-protocol.md)允許的規劃路徑。

## 1. 鎖定來源與證據

依序解析本次唯一來源規格：

1. 使用者明確提供的檔案、URL、issue 或對話內容。
2. 適用治理指定的規格來源。
3. 工作區中唯一能明確對應本次成果的規格。

若有多個合理候選，列出已找到的位置，並以本回合唯一問題請使用者指定。

從來源擷取目標、範圍外項目、規範性需求、驗收情境、品質屬性、技術限制及相容／移轉條件，建立 `需求 → 設計 → 測試 → 工作包` 的內部覆蓋圖。

先讀適用的 `AGENTS.md` 與治理，再依規格影響範圍檢查 README、領域詞彙、ADR、manifests、lockfiles、版本與入口、受影響模組／資料／契約、測試、CI、支援環境及相關 Git 歷史。使用 `rg` 或 `rg --files` 定位；沒有應用程式碼是 greenfield 現況證據。

時效敏感的技術事實使用官方文件、標準、上游原始碼或第一方 API，記錄版本、日期與直接連結。所有主張分成：

- `Observed`：專案或實際執行已確認。
- `Required`：來源規格或治理強制要求。
- `Proposed`：規劃選擇，尚未實作或執行。

**完成條件：** 來源規格與規劃邊界唯一且可引用；每項可能改變設計、測試或工作包的可取得事實都有來源，未檢查區域未被描述成已理解。

## 2. 通過證據門檻

將每個未知或矛盾分類並走唯一適用分支：

1. `需求缺口`：會改變使用者可見行為、範圍或驗收。交回 `requirements-discovery`；不可用時精確說明缺口與影響。
2. `可研究事實`：由專案證據或一手來源自行查證。
3. `技術決策`：呈現雙方證據、可行選項、取捨、影響及有依據的建議，每回合只問一項最高影響決策。
4. `必要證據不可得`：列出已查位置、缺失證據及受影響的設計、測試與工作包，進入 `Blocked`。

規格、現有行為與治理衝突時，引用衝突雙方並指出各選擇影響的需求、Modules、測試與工作包。只有不會改變設計、測試策略或工作包的事項可安全延後。

任一阻塞分支成立時，完整閱讀[交付協定](references/delivery-protocol.md)並執行 `Blocked` 分支；本回合停在需求探索交接、唯一技術決策或 `Blocked`，不載入 Candidate 撰寫資料。

**完成條件：** 需求缺口、證據矛盾與阻塞未知皆為零；否則已依交付協定停在單一、明確的解除阻塞動作。

## 3. 撰寫 Candidate

只有證據門檻通過後，才完整閱讀[Candidate 撰寫準則](references/candidate-authoring.md)與[技術規劃模板](references/technical-plan-template.md)。依兩者形成 current state、target state、技術決策、Modules／Interfaces／Seams、測試策略、垂直工作包、風險、追溯及自適應 artifact bundle。

Current state 只使用 `Observed` 證據；新檔案、signatures、介面與架構均標為 `Proposed`。

**完成條件：** 模板的所有必要內容已完成，每項適用規範性需求都連到設計、可判定驗證與至少一個工作包，Candidate 中沒有阻塞未知。

## 4. 驗證與交付

完成草稿後完整閱讀[品質契約](references/quality-contract.md)，逐項二元檢查。失敗項目回到對應階段修正；必要證據或決策不可得時改走交付協定的 `Blocked` 分支。

品質契約全部通過後，完整閱讀[交付協定](references/delivery-protocol.md)，只執行符合目前狀態的分支。該協定是狀態、建議路徑、完整 Candidate 展示、修改、核准與防覆寫的唯一權威。

**完成條件：** 本回合明確停在 `Blocked`、等待唯一技術決策、`Candidate—Awaiting confirmation`，或已依核准內容寫入 `Ready` artifacts。

維護或修改本 Skill 時，才完整閱讀[行為驗證契約](references/behavior-evaluation.md)並執行全部適用案例；一般技術規劃不載入該文件。
