# 需求探索

把不完整、矛盾或尚未驗證的產品與軟體構想，逐步轉成可驗收、可追溯，且足以進入技術規劃的需求分析。保持內容精簡，但不可用精簡掩蓋未決事項。

## 核心界線

- 探索 `為什麼`、`要什麼`、`由誰使用`、`何時成立` 與 `如何驗收`。
- 不決定架構、技術選型、檔案、類別、API 內部設計、實作步驟或工作拆分；只記錄外部已強制的技術限制。
- 不撰寫程式碼，不在探索期間開始實作。
- 使用者對探索問題的回答不是寫檔授權，也不是開始實作的授權。
- 使用使用者的主要語言提問與成文；保留必要的領域原文，所有識別碼維持 ASCII。
- 對多個可獨立規劃、驗收或發布的子系統，先說明拆分方式與依賴，再一次完成一份可獨立規劃的文件。

## 探索流程

### 1. 先查明可取得的事實

在提問前，檢查目前可用的專案脈絡，包括適用的 `AGENTS.md`、治理文件、README、既有規格、領域詞彙、資料模型、介面、程式碼與近期變更。必要且獲准時，再查外部的一手資料。

- 自己查找可從專案或可靠來源取得的事實，不把研究工作轉嫁給使用者。
- 只詢問需要人做決定、確認優先順序或提供無法存取資訊的事項。
- 若必要事實無法取得，先簡述已查過的位置，再把它當成本輪唯一問題。
- 不因初始描述很長就假定需求完整，也不因描述很短就一次拋出問卷。

### 2. 建立工作中的覆蓋圖與決策樹

維護內部工作表，將每個適用項目標成 `已確認`、`未知`、`矛盾` 或 `不適用`。不要展示隱藏推理或分數；可向使用者簡潔說明已知內容與目前缺口。

逐項判斷下列覆蓋面是否適用：

1. 問題、價值、為何現在做、預期成果
2. 利害關係人、使用者、系統角色與決策權
3. 範圍、非目標、優先順序與發布邊界
4. 現況流程、目標流程、主要與替代旅程
5. 功能行為、業務規則、權限與狀態轉換
6. 領域詞彙、資料、實體、所有權與生命週期
7. 外部整合、上下游、契約與失敗處理
8. 使用體驗、無障礙、在地化與人工介入
9. 效能、可用性、安全、隱私、稽核等品質屬性
10. 邊界條件、錯誤、重試、復原與降級
11. 限制、依賴、移轉、相容性與過渡需求
12. 風險、法規、政策與必要的人工作業審查
13. 驗收條件、成功指標、來源與追溯關係

只有在有事實支持時才標記 `不適用`。所有適用且會影響範圍、行為、風險或驗收的未知事項都必須釐清；不可用未經確認的預設值補洞。純技術規劃決策則明確延後，不當成需求缺口。

把決策依前置關係排成樹。只有前置決策已解決的未知節點，才能進入當前可提問的 frontier。

### 3. 每輪只問一個最高價值問題

每個回合只能提出一個需要使用者回答的問題。依 `影響程度 × 不確定性 × 不可逆性` 選擇 frontier 中最高價值的節點；同分時依序處理：

1. 範圍與業務成果
2. 法規、安全與隱私
3. 驗收與可測試性
4. 角色、業務規則與資料
5. 使用體驗
6. 營運限制與外部技術限制

問題必須：

- 可單獨理解，先用一至兩句說明已知脈絡與這項決定的影響。
- 在適合時提供二至四個互斥且有實質差異的選項，簡述各自後果，並允許簡短自訂答案。
- 只有在專案證據、一手資料或清楚的領域慣例支持時才推薦選項；若沒有可靠依據，明說不偏好任何選項。
- 讓使用者能只回覆選項標籤或一句話。
- 不附帶第二個問題，也不以「還有其他嗎」結尾。

若答案含糊、互相衝突或引入新的高影響歧義，下一輪仍只釐清同一決策。每次收到答案後更新覆蓋圖、決策樹與 frontier，再選下一題。沒有固定題數上限。

### 4. 主動檢查矛盾與過度擴張

- 對同一詞彙的不同含義，先建立明確定義再繼續。
- 對互斥回答、與現有系統不一致的敘述或不可驗收的形容詞，指出具體衝突並要求一個決定。
- 新增需求若跨出目前成果邊界，標出其影響，確認納入、延後或拆成另一份文件。
- 若輸入包含多個獨立子系統，先提出最小可規劃的拆分與建議順序；需要選擇時，把「先處理哪一份」作為唯一問題。

### 5. 處理高風險或受規範需求

只要需求可能涉及法規、合約、安全、隱私、醫療、金融、兒少、身分或其他高風險領域：

1. 優先釐清適用司法管轄區、框架、版本、資料類型與責任角色。
2. 查閱官方法規、標準發布者或主管機關的一手來源；記錄連結與存取日期。
3. 將每項適用義務映射到 `CR-*` 需求、驗收證據與負責的人工作業審查者。
4. 把未確認的法律解讀標成待專業審查，不宣稱產品或文件已合法、已認證或完全合規。
5. 若關鍵一手來源或適格審查者不可得，將文件標成 `Blocked`，不要以推測通過品質門檻。

### 6. 判定探索是否完成

只有同時符合下列條件才停止提問：

- 所有適用且具實質影響的決策都已確認，frontier 與其後續未知節點皆為空。
- 沒有未解矛盾、未定義關鍵詞或阻塞驗收的開放事項。
- 每個需求都能對應業務成果、旅程或利害關係人需求，並有可觀察的驗收方式。
- 外部強制限制、依賴、風險、過渡條件與成功衡量方式已清楚。
- 剩餘事項只屬技術規劃，而且已明確標記為後續決策。

完成時，依序完整閱讀：

1. [品質契約](references/quality-contract.md)
2. [需求分析模板](references/requirements-analysis-template.md)

先套用品質契約自我檢查；任何關鍵項目未通過，就回到一次一題的探索，不要產生 Ready 文件。

### 7. 先展示，再取得寫檔同意

通過 AI 品質檢查後：

1. 依模板在對話中產生完整文件草稿，狀態使用 `Candidate—Awaiting confirmation`。
2. 決定並顯示精確的建議路徑。優先順序為：使用者指定路徑、專案治理或輸出設定、預設的 `docs/requirements/YYYY-MM-DD-<topic>.md`。
3. `<topic>` 使用二至五個小寫 ASCII kebab-case 單字；必要時翻譯或音譯主題。
4. 先檢查檔案是否存在。若已存在，不覆寫；提出加上 `-2`、`-3` 等最小可用後綴的新路徑。
5. 只問一個明確的是非題：是否確認這份完整內容，並寫入所示路徑？

必須等使用者在看過完整草稿與精確路徑後明確肯定，才可在下一輪寫檔。先前的「幫我產出文件」或探索回答不算確認。若使用者要求修改，更新內容、重新檢查並再次展示後再詢問。寫入時把狀態改為 `Ready`，內容必須與確認版本一致。

### 8. 提前停止與實作請求

- 若使用者在探索未完成時要求停止或索取目前成果，產生 `Draft—Not ready`，列出已確認內容、未決事項、各缺口的影響與下一個必要決策；不得宣稱可進入規劃或已符合品質門檻。
- 提前草稿若要寫檔，仍需先展示完整內容與路徑，再取得單獨的明確同意。
- 若使用者在探索中要求實作，說明目前是否已 Ready。尚未 Ready 時，把「繼續探索，或以 `Draft—Not ready` 結束」作為本輪唯一問題；不得實作。Ready 後則明確結束探索並交接給技術規劃，不在本 Skill 內寫程式碼。

## 最終輸出要求

- 只保留適用內容；省略空白、重複與純粹標示「不適用」的章節。
- 不收錄逐題訪談逐字稿，只保留已確認決策及其來源。
- 使用穩定識別碼與規範性文字，建立 `業務成果 → 旅程 → 需求 → 驗收情境 → 成功指標` 的追溯。
- 內容須足以交給技術規劃，但不得偽裝成架構設計或實作計畫。
