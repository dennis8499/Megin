# 需求探索交付協定

只有在探索通過品質門檻，或使用者要求提前停止、索取目前成果或開始實作時，才完整閱讀並執行本協定。每次只走一個符合目前狀態的分支。

## 文件狀態

- `Draft—Not ready`：仍有可繼續釐清的實質需求缺口、矛盾或不可驗收內容。
- `Blocked`：關鍵決策者、必要事實、一手規範來源或適格審查者不可得，無法可靠完成。
- `Candidate—Awaiting confirmation`：品質契約全部通過，完整內容正等待使用者確認。
- `Ready`：品質契約全部通過，且使用者已確認完整內容；可交給技術規劃。

一份文件同時只能有一個狀態。使用者對探索問題的回答、先前要求產出文件或一般性的寫檔授權，都不會自行改變狀態。

## 建議路徑

需要建議寫檔位置時，依序採用：

1. 使用者在本次需求探索中指定的路徑。
2. 適用的專案治理或輸出設定。
3. `docs/requirements/YYYY-MM-DD-<topic>.md`。

`<topic>` 使用二至五個小寫 ASCII kebab-case 單字，必要時翻譯或音譯主題。顯示路徑前先檢查檔案是否存在；已存在時保留原檔，使用 `-2`、`-3` 等最小可用後綴。

## 品質門檻已通過

1. 完整閱讀[需求分析模板](requirements-analysis-template.md)。
2. 依模板在對話中展示完整文件，狀態設為 `Candidate—Awaiting confirmation`。
3. 顯示精確的建議路徑。
4. 以本回合唯一問題詢問：「是否確認上述完整內容，並同意寫入 `<path>`？」

**本回合完成條件：** 使用者已看到完整內容與精確路徑、只收到一個確認問題，而且檔案系統尚未變更。

下一輪依使用者回覆處理：

- 明確肯定且清楚指向該版本與路徑：寫入前再次確認路徑仍不存在，再把文件狀態改為 `Ready` 並寫入。除狀態與確認者資訊外，其餘內容必須與確認版本一致。
- 路徑在確認後已被占用：保留既有檔案，改用最小可用後綴；以新路徑重新展示確認問題，該輪不寫檔。
- 要求修改：更新需求內容，重新執行品質契約，展示新的完整 Candidate 與路徑，再取得新的明確確認。
- 回覆含糊或未清楚指向該版本與路徑：以單一問題重新確認，該輪不寫檔。

## 提前停止或索取目前成果

1. frontier 尚有可繼續釐清的缺口時，使用 `Draft—Not ready`；必要來源、決策者或審查者不可得時，使用 `Blocked`。
2. 完整閱讀[需求分析模板](requirements-analysis-template.md)，在對話中產生自足的目前成果，列出已確認內容、未決事項、各缺口影響與下一個必要決策。
3. 明確聲明文件尚不可作為無條件的技術規劃基準。
4. 使用者若要求寫檔，先展示完整內容與精確路徑，再以唯一問題取得針對該版本與路徑的明確同意；寫入後仍維持 `Draft—Not ready` 或 `Blocked`。

**分支完成條件：** 文件狀態忠實反映缺口，沒有 Ready 聲明；任何寫檔都發生在完整展示與單獨確認之後。

## 探索期間要求實作

- 文件尚未 `Ready`：說明目前缺口，並把「繼續一次一題的探索，或依提前停止分支產生 `Draft—Not ready`／`Blocked`」作為本回合唯一問題。探索期間不開始實作。
- 文件已 `Ready`：明確結束需求探索，把 Ready 文件與尚待決定的純 HOW 項目交給技術規劃；本 Skill 不撰寫程式碼。
