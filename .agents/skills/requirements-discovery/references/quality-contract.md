# 需求分析品質契約

本契約只判定需求分析是否通過二元品質門檻；文件狀態、展示與寫檔規則由[交付協定](delivery-protocol.md)定義。契約借鏡 [ISO/IEC/IEEE 29148:2018](https://www.iso.org/standard/72089.html) 的需求工程觀念與 [IIBA《The Business Analysis Standard》](https://www.iiba.org/globalassets/business-analysis-resources/the-business-analysis-standard/files/the-business-analysis-standard.pdf) 的商業分析實務，但不代表取得認證，也不構成對任何標準、法規或合約的符合性聲明。

## 單一需求品質門檻

逐條檢查每個 `BR-*`、`UR-*`、`FR-*`、`NFR-*`、`TR-*` 與 `CR-*` 需求。每項都必須符合：

1. **必要且有來源**：能連到已確認的業務成果、旅程、利害關係人決定、現有契約或一手規範。
2. **正確**：忠實反映可驗證的專案事實或已確認決策，不把推測寫成事實。
3. **單一**：一個識別碼只表達一項可獨立驗證的義務；避免以「以及」綁定多種行為。
4. **明確**：角色、觸發、條件、行為、資料與結果足以排除合理的不同解讀。
5. **完整**：必要的前置條件、例外、邊界與失敗結果都有定義或可追溯連結。
6. **一致**：不與其他需求、詞彙、流程、資料生命週期或範圍決策衝突。
7. **可行**：在已知業務、法規、營運與外部限制內可實現；未知可行性不得被隱藏。
8. **可驗證**：有可觀察的通過或失敗結果，並連到至少一個驗收情境或客觀證據。
9. **可追溯**：具有唯一且穩定的識別碼，能向上追溯來源，向下追溯驗收與衡量方式。
10. **適當層級**：描述外部可見需求與限制，不預先指定架構、程式碼、檔案或工作任務。
11. **規範性**：義務使用一致、明確的「必須」或「不得」；不使用「最好」、「盡快」、「容易」、「適當」等未量化形容詞。

對品質屬性，另須記錄適用條件、衡量方式、門檻與觀察期間；例如百分位、資料量、服務時段或復原時間，而非只寫「快速」或「高可用」。

## 整份文件品質門檻

只有以下各項全部通過，整份文件品質門檻才算通過：

- 問題、目前影響、為何現在做與預期業務成果彼此一致。
- 利害關係人、使用者、系統角色與決策責任清楚。
- 範圍內、範圍外、非目標、優先順序與發布邊界清楚。
- 每個適用角色都有端到端主要旅程；重要替代、邊界、失敗、復原與人工介入均已涵蓋。
- 適用的資料、實體、狀態、生命週期、權限、整合與來源真相已定義。
- 適用的安全、隱私、稽核、效能、可靠性、無障礙與在地化需求可衡量、可驗收。
- 移轉、相容性、過渡、營運依賴與外部強制限制沒有被遺漏。
- 每個成功指標都有基準或明確的基準取得方式、目標、量測期間與責任來源。
- 文件沒有衝突、重複需求、未定義關鍵詞、空白章節、未確認假設或阻塞性開放問題。
- 文件不包含 HOW：沒有架構選型、內部 API 設計、檔案清單、程式碼結構、實作步驟或任務拆分；外部強制限制除外。
- 追溯表完整連接 `業務成果 → 使用者旅程 → 需求 → 驗收情境 → 成功指標`，且不存在孤立需求。
- 文件的狀態、日期、範圍、來源與確認者可識別。

## 驗收情境門檻

每個驗收情境都必須：

- 使用唯一的 `AC-*` 識別碼。
- 以 Given／When／Then 或同等明確格式描述前置狀態、事件與可觀察結果。
- 涵蓋對應需求的正常路徑；高風險、邊界或失敗需求另有負向或復原情境。
- 不依賴讀者推測測試資料、角色權限或成功標準。
- 驗證需求結果，不鎖定內部實作方法。

## 高風險與規範加強門檻

需求涉及法規、契約、安全、隱私、醫療、金融、兒少、身分或其他高風險領域時，必須額外通過：

- 已確認司法管轄區、適用框架、版本或生效日期、資料分類與責任角色。
- 每項規範義務都有 `CR-*` 識別碼，且映射到官方主管機關、法規或標準發布者的一手來源。
- 引用記錄來源名稱、直接連結、版本或日期、存取日期與適用性理由。
- 每項 `CR-*` 都有驗收證據及具名角色的人工作業審查責任；AI 不取代法律、資安、隱私或產業專家。
- 對未解釋、地域差異、例外條款或待審意見明確標成阻塞，不以常識補齊。
- 文件只陳述「已映射的需求與待驗證證據」，不宣稱產品合法、已認證或完全合規。

合規追溯至少包含：

| 欄位 | 必要內容 |
|---|---|
| 規範需求 | `CR-*` 與明確義務 |
| 適用依據 | 司法管轄區、產品／資料情境、框架與版本 |
| 一手來源 | 發布機關、直接連結、版本／日期、存取日期 |
| 驗收證據 | 可檢查的紀錄、行為、報告或控制結果 |
| 人工審查 | 負責角色、審查範圍與尚待確認事項 |

## 二元判定

依序逐條驗證單一需求、驗收情境、整份文件與雙向追溯；高風險或受規範需求再執行加強門檻。

- **通過：** 每個適用檢查都有可核對的需求內容、來源或驗收證據，沒有失敗項目。
- **未通過：** 任一適用檢查缺少證據或不符合門檻。把失敗項目轉回覆蓋圖中的 `未知` 或 `矛盾`，繼續一次一題的探索。
- **無法完成：** 關鍵決策者、必要事實、一手來源或適格審查者不可得。依[交付協定](delivery-protocol.md)進入阻塞分支。

品質契約通過只授權進入交付分支，不構成寫檔或實作授權。
