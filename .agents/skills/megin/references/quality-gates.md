# Quality evidence and gate boundaries

This reference applies to new or resumed change work. Keep the approved plan as the sole source of required behavior, commands, and paths; `workflow.md` remains the status surface. A `quality_ref` points to execution evidence, not a second plan or phase controller. Completed historical records are not retroactively rewritten.

## Plan and implementation

For each observable result, name the assertion that proves it, the test and exact command, and any required environment. Split unrelated results rather than claiming that one `SCN-*` tag proves all of them. Identify failure, retry, restart, concurrency, and external-dependency checks only where the change makes them relevant. Existing meaningful coverage can be reused without manufacturing a red test.

For new behavior, keep the failing behavior assertion and subsequent passing command with their own snapshots and raw output. A compiler error or missing entry point is a setup failure, not sufficient behavior-red evidence. A passing parser, configuration-value check, mock, or unrelated test is not end-to-end proof. The writer must describe the observable promise and the assertion that would fail if its essential behavior were absent.

## Independent review

The reviewer is a different fresh read-only context. Save the actual invocation/source and raw result, not merely a writer-authored claim of independence. If no such reviewer exists, remain `awaiting_review`. The reviewer inspects the full change and, separately, traces each important promised result through implementation and test assertions. Findings name the missing observable behavior, source location, and correction. The reviewer must not approve code it wrote.

## Snapshots and evidence

An approved plan and feature contract are protected alongside product, tests, configuration, documentation, and distribution content. A product snapshot includes tracked, unstaged, deleted, and non-ignored untracked paths using the Git-normalized blob identity that staging would produce. Before acceptance, staged product changes are rejected. The protected digest excludes only `workflow.md` and exact evidence paths predeclared in the approved contract's `process_records`; executable checks or fixtures under the Work ID remain protected unless the plan explicitly classifies that exact path as a process report. Preserve a separate digest for every cited process record. Appending a predeclared process record does not change the approved product snapshot, while editing or deleting cited evidence invalidates that citation. Do not make a blanket `docs/work/**` or `evidence/**` exclusion.

Red evidence points to the failing preimplementation snapshot. Green, review, final verification, and human acceptance point to the same current product and approved-contract snapshot. A product or contract change invalidates later approvals and returns to the affected work, review, verification, and acceptance steps under branch policy. Never silently refresh a digest to make stale evidence look current.

## Gate outcomes

For a new Work ID, the approved plan binds `plan-<version>/quality-contract.json` (`megin-quality-contract/v1`) with `work_id`, `plan_version`, exact `allowed_paths`, exact `process_records`, and required `checks` (`id`, `kind`, `command`). The Work ID's `workflow.md` adds `quality_ref` to an `evidence/quality.json` file (`megin-quality-evidence/v1`). Paths must be canonical repository-relative paths without `.` or `..`; every cited source must resolve inside this Work ID's evidence directory and be an approved process record. The evidence records the current `snapshot` digest, writer context and raw source reference, a `sources` list for other cited reports, each command's ID/status/exit code/snapshot/output reference and, for tests, executed/failed/skipped counts. Review adds reviewer context/verdict/snapshot/raw source; acceptance adds Work ID/version/verdict/snapshot/raw source. A source reference has a repository-relative `path` and SHA-256 of its actual bytes. Its `claims` map gives a one-based line and exact text for every structured identity or outcome copied from that source. Writer handoff sources contain `- context:` and `- snapshot:`; review sources contain `- context:`, `- verdict:`, and `- snapshot:`; acceptance sources contain `- work_id:`, `- version:`, `- snapshot:`, and `- verdict: ACCEPTED`. All values are nonempty strings and must match those exact hashed source lines. Command logs contain `Command:` and `Exit code:` claim lines plus a separate result locator. This prevents a structured `APPROVED`, `ACCEPTED`, command, or exit code from contradicting its raw source. For a custom test script without a framework count, count one executed script only if it reached a real assertion; cite its output line and assertion source for the reviewer. The plan defines obligations; evidence cannot drop an approved check. Preserve tool output and cite where every extracted count came from. Do not infer that a digest proves the report itself is truthful.

- `review`: exact approved scope and branch, writer handoff, every required command result and raw source reference, and current snapshot are present. Results may report a real failure at this handoff; this gate checks completeness and does not turn it into a pass. This gate does not require a review that has not yet occurred.
- `acceptance`: a different reviewer returned `APPROVED` for the current snapshot, and all approved automated obligations on that snapshot passed. A required command with nonzero exit, no executed tests, failures, skips, `blocked`, `not_run`, missing output, or an unknown result stops the gate. Environment failure is recorded as `blocked`, not waived.
- `delivery`: run after staging. The user's explicit Work ID and acceptance version bind the same product snapshot; no protected product path remains unstaged or untracked, and the SHA-256 manifest over staged Git blob identities equals the accepted product manifest. The output lists staged protected paths and the staged digest for audit. The target base branch, approved paths, and cited evidence remain unchanged. Knowledge promotion after acceptance must follow its approved scope and the branch-policy recovery rule for any resulting snapshot change.

The checker may validate identifiers, path/digest references, exit codes, numeric test counts, and these fixed transitions. It cannot decide whether an assertion proves the promised behavior or whether a human reviewer actually reasoned independently. The model handles those judgment calls and cites the underlying source. Never report a structural gate result as proof that the product works.

After each work package, record what was completed, what was verified, what remains uncertain, and the next action.
